# 협업 가이드 (CONTRIBUTING)

## 0. 작업 흐름 한눈에 보기

1. Issue 생성 (작업 1개 = Issue 1개)
2. 최신 `main`에서 브랜치 생성: `git switch -c <type>/<id>-<작업>`
3. 컨벤션에 맞춰 커밋
4. push 후 PR 생성 (본문에 `Closes #이슈번호`)
5. 리뷰 1명 이상 승인 → 작성자가 merge
6. merge 후 로컬 브랜치 정리: `git switch main && git pull && git branch -d <브랜치>`

## 1. 브랜치 네이밍 규칙

형식: `<type>/<id>-<작업>`

- `<id>`는 본인 GitHub 아이디를 사용 (예: `sw0410`).
- `<작업>`은 작업 내용을 영문 소문자로 짧게 작성하고 단어는 `-`로 연결.
- 기본 작업 브랜치는 `feature/<id>-<작업>`을 사용.
- 오류 수정은 `fix/`, 문서 작업은 `docs/`도 사용 가능. 

| type | 용도 | 예시 |
| --- | --- | --- |
| `feature` | 기능·결과물 추가 | `feature/<id>-add-team-intro` |
| `fix` | 잘못된 내용 수정 | `fix/<id>-readme-link` |
| `docs` | 문서 작업 | `docs/<id>-contributing-review-rule` |

- `main`에 직접 push 하지 않습니다 (Branch Protection으로 막혀 있음).
- 브랜치는 PR을 머지한 직후 PR 페이지의 **Delete branch** 버튼으로 삭제합니다.

## 2. 커밋 메시지 컨벤션

형식: `<type>: <무엇을 바꿨는지>` (한글 가능, 50자 이내)

| type | 의미 |
| --- | --- |
| `feat` | 새 기능 / 결과물 추가 |
| `fix` | 오류 수정 |
| `docs` | 문서 추가·수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정, 폴더 구조 등 기타 |

좋은 예:
- `docs: CONTRIBUTING에 리뷰 최소 기준 추가`
- `feat: 홍길동 팀 소개 파일 추가`
- `fix: README의 conflict 문서 링크 경로 수정`

금지 (의미 없는 메시지):
- 대상을 알 수 없는 단어만: `update`, `fix`, `temp`, `wip`, `final`
- 무엇을/왜가 없는 것: `bug fix`, `edit file`

## 3. PR 작성 규칙

- 작업은 Issue로 등록하고 작업 브랜치에서 진행
- PR의 병합 대상은 'main'으로 지정
- 제목: 커밋 컨벤션과 같은 형식 (`docs: ...`)
- 본문은 템플릿(`.github/pull_request_template.md`)을 따르며 아래 항목은 필수
  - **What**: 변경한 파일과 주요 변경 사항
  - **Why**: 변경이 필요한 이유
  - **How**: 실제 수행한 검증 방법과 결과
  - **관련 Issue**: `Closes #이슈번호` 또는 `Fixes #이슈번호`
- 한 PR에는 한 가지 목적의 변경을 담음.
- PR 생성 후 다른 팀원을 리뷰어로 지정.
- 리뷰 의견에 대응하고 모든 리뷰 대화가 해결(Resolved) 상태이며 다른 팀원 최소 1명의 승인을 받은 뒤 작성자가 병합. 
- 병합은 `Create a merge commit` 방식을 사용.
- 충돌이 있으면 해결 및 검증을 마치고 리뷰어에게 재확인을 요청.
- 각 팀원은 최소 2개의 PR을 생성하고 병합. 

## 4. 코드 리뷰 규칙

### 리뷰어

- 본인 PR을 제외한 다른 팀원의 PR을 최소 2개 리뷰하기.
- 각 PR에 실질적인 리뷰 코멘트를 최소 1개 남기기.
- 코멘트에는 특정 파일이나 라인을 근거로 질문, 대안, 위험요소, 개선 제안 중 하나 이상을 작성하기.
- `LGTM`, `좋아요`만으로 리뷰를 끝내지 않기.
- 수정이 반드시 필요하면 `Request changes`를 사용하고 제안이나 질문은 `Comment`로 남기기.
- 수정 결과와 작성자의 답변을 확인한 뒤 해결된 리뷰 대화는 리뷰어가 `Resolve conversation`으로 종료하기.
- 병합 가능한 상태이면 승인하기. 
- 사람을 평가하지 않고 변경 내용에 대해 이유를 들어 설명하기. 

### PR 작성자

- 리뷰 의견에 답글 또는 수정 커밋으로 대응하기.
- 의견을 반영한 경우 변경 내용과 확인 결과를 답글로 남기기.
- 반영하지 않는 경우에는 이유를 설명하고 리뷰어와 논의하기.
- 수정 후 리뷰어에게 재확인을 요청하기.
- 각 PR에는 작성자와 리뷰어 간 최소 1회 이상의 상호작용 기록을 남기기.
- 각 팀원은 본인 PR 중 최소 1개에서 리뷰 의견을 반영하고 관련 커밋 또는 답글을 증빙으로 남기기.

### 리뷰어 자동 지정 (CODEOWNERS)

- `.github/CODEOWNERS`에 경로별 담당자를 지정해 두어, PR을 열면 바뀐 파일의 오너가 리뷰어로 자동 요청됩니다.
- 모든 경로에 오너를 2명 이상 둡니다. GitHub은 PR 작성자에게 리뷰를 요청하지 않아서, 오너가 1명이면 그 사람이 작성자일 때 요청될 사람이 없기 때문입니다.
- **Require review from Code Owners**는 켜지 않습니다. 켜면 오너가 서로 다른 파일(예: 작업 파일 + 기록 파일)을 함께 바꾸는 PR은 승인이 2개 이상 필요해집니다. 자동 지정만으로 미션 요구를 충족합니다([#20](https://github.com/On-Premise-Sky/B2-2/pull/20)).
- PR 작성자는 리뷰 짝(A 이승우 ↔ B 김영운, C 김나현 ↔ D 안시우)을 리뷰어로 직접 지정합니다. 승인은 1명이면 됩니다.

## 5. 충돌 발생 시 대응 흐름

| 단계 | 누가 | 어떻게 |
| --- | --- | --- |
| 1. 발견 | PR 작성자 | PR에 "conflicts" 표시 확인 또는 merge 시 충돌 |
| 2. 공유 | PR 작성자 | 팀 채널에 충돌 파일과 상대 PR 공유 |
| 3. 해결 | PR 작성자 (필요하면 상대 작성자와 함께) | 로컬에서 `git pull origin main` → 마커 정리 → 커밋 |
| 4. 확인 | 리뷰어 | 해결 결과가 양쪽 의도를 모두 반영했는지 리뷰 |
| 5. 기록 | 해결한 사람 | `docs/conflict-resolution.md`에 템플릿대로 기록 |

### 작업 시작 전

여러 명이 같은 파일을 고칠 때는 **같은 커밋에서 분기**해야 충돌 지점이 분명해집니다.

```bash
git switch main
git pull origin main
git switch -c <type>/<id>-<작업>
```

### 머지 순서

같은 파일을 고치는 PR이 여러 개면 머지 순서를 미리 정합니다.

- 머지한 사람은 팀 채널에 "#번호 머지함"이라고 알립니다.
- 다음 순서인 사람은 알림을 받은 뒤 자기 브랜치에서 main을 받아옵니다.

```bash
git fetch origin
git merge origin/main
```

- 여기서 충돌이 나면 main에 병합하기 전에 로컬에서 해결합니다.
- 해결 후에는 리뷰어에게 재확인을 요청합니다.

### 기록 항목

`docs/conflict-resolution.md`에는 다음 순서로 적습니다. 다른 사람이 같은 상황을 재현할 수 있어야 합니다.

1. 상황: 누가, 어떤 파일에서, 왜 충돌했는지
2. `git status` 출력
3. 충돌 마커 전후 코드
4. 선택한 결과와 그 이유
5. 검증 방법: 로컬에서 무엇을 어떻게 확인했는지
6. 주의점

주의: 공유 브랜치(`main`)에는 `--force` push, rebase 금지. 개인 feature 브랜치의 히스토리 정리는 팀에 먼저 알린 뒤 진행합니다. 자세한 기준은 6장을 따릅니다.


## 6. 히스토리 정리 (`git rebase -i`)

### 기준

- 히스토리 정리는 본인 작업 브랜치에서, push하기 전 로컬 커밋에만 합니다.
- 오타 수정·자잘한 보완 커밋은 관련 커밋에 `squash`(또는 `fixup`)로 합칩니다.
- `update`, `wip`처럼 컨벤션에 맞지 않는 메시지는 `reword`로 고칩니다.
- 정리 전에 `git branch backup/<브랜치>`로 백업하고, 정리 후 `git diff backup/<브랜치> HEAD` 결과가 비어 있는지 확인합니다(내용은 그대로, 커밋만 정리).
- 이미 push한 커밋을 정리해야 하면 팀에 먼저 알리고 `git push --force-with-lease`를 사용합니다. `main`에는 하지 않습니다.
